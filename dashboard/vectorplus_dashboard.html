04 QBit — precision chosen at query time The same rows with the vector stored as bit planes. No index: every query scans every row ▼
QBit stores each Float32 as 32 bit planes. L2DistanceTransposed(embedding, vector, bits) reads only the top bits planes of every number, so one table serves every precision and the trade-off is made per query, with nothing to build or tune in advance. It is a brute-force scan, so latency grows with the table; reading fewer bits saves I/O, not the work of rebuilding each number. The table is made from ch_docs inside ClickHouse, then checked against it. The sweep maps the shared probes value p to min(p, 32) bits.

01 How points are counted Five steps, no hidden factors — every number below can be reproduced by hand ▼

① Measure

Each engine has up to six measurements from a saved sweep: latency at the recall bar, p95 latency, best recall reached, build time, index size, and maintenance (churn) time.

② Compare with the best

For each measurement the best engine in the ranking sets the yardstick. An engine's ratio is best ÷ value (value ÷ best for recall). The best scores 1.0; twice as slow or twice as large scores 0.5.

③ Weight

Each measurement is worth a share of 100 points in proportion to its weight. Measurements that are switched off or missing for any engine are dropped, and the rest are rescaled to still add up to 100.

④ Add up

Points for a measurement = its share × the ratio. The score is the sum, so 100 is only possible by being best at everything.

⑤ Gate

An engine that never reaches the recall bar is DNQ: it gets 0 points for latency and p95, and is ranked below every engine that did reach it, whatever its score.
share(metric) = 100 × weight(metric) ÷ (sum of the weights in use)
ratio = best ÷ value   (latency, p95, build time, index size, maintenance — lower is better)
ratio = value ÷ best   (best recall — higher is better)
points(engine, metric) = share(metric) × ratio
score(engine) = Σ points(engine, metric)

06 Rules, edge cases and how to read the result The things that surprise people ▼
  • The "best" depends on who is ranked. Untick an engine on the Benchmark tab and every other engine's ratios — and points — change, because the yardstick moves.
  • A DNQ engine's score can look higher than a ranked one's. It keeps the points it earned on recall, build time and size, but it is placed below every engine that reached the bar. The gate decides the order; the score does not. On the Benchmark tab its score is shown greyed in brackets for that reason.
  • Ties in score are broken by the lower latency at the bar.
  • Ratios compress big gaps. An engine 3× slower than the best earns a third of the latency points; one 30× slower earns almost none, and so does one 300× slower. Differences between the slowest engines barely show in the score — look at the latency column and the charts for those.
  • Rounding: points are computed from unrounded measurements, so adding the rounded figures shown can differ by a tenth.
  • The score is a summary, not a measurement. Changing the weights can change the order. The measurement columns and charts are the evidence; the score is one way of weighing them.
  • WarehousePG engines are not on the same hardware as the Postgres ones. Queries run on every segment in parallel, and probes apply per segment, so their lead in latency is not a like-for-like win over a single node.
  • Runs are comparable only if their setup is. Different k, probe lists, cache mode or data change the numbers; the Benchmark tab warns when scaling runs differ.
  • "DNQ" can mean "needs more probes". If the probe list stops at 32 and an engine reached 88% there, it may reach the bar at 64 or 128. Extend the list before concluding it cannot.
  • The data is synthetic unless you loaded your own. Confirm any ranking on your own embeddings before deciding.
